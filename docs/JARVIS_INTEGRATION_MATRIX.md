## Existing architecture and ownership

```text
Identity/auth (core + auth router)
  → owned ChatService conversation/session store
  → existing CapabilityRegistry/Orchestrator, Tool/MCP, Memory/RAG
  → ProviderGateway → provider fabric / Silverwing ModelRouter / Brain
  → existing event_fabric → RuntimeEventService projection
  → authenticated snapshot + SSE → frontend RuntimeBridge/store
  → Presentation Intelligence planner + capability presentation bindings
  → negotiated React renderer/client surface
```

Authority stays with the existing component for each concern: auth owns identity, backend policy owns authorization, ChatService owns conversations, ProviderGateway/ModelRouter owns inference routing, CapabilityRegistry/Orchestrator owns capability execution, the task subsystem owns its jobs, RuntimeEventService projects runtime truth, and the presentation planner chooses semantic intent. React and routes do not authorize or execute privileged actions.

## Authentication and persistence details

- **Identity endpoints:** `jarvis_backend/routers/auth.py` owns login, registration, logout, refresh, identity retrieval/update, password reset/change, email verification/resend, session and API-key management.
- **Password storage:** `core.py` hashes with Argon2id and verifies/upgrades legacy PBKDF2/HMAC hashes.
- **Tokens:** HS256 signed tokens; access lifetime is one hour, refresh lifetime is 24 days and refresh tokens rotate/revoke. Production signing key is expected from configuration; development can use an ephemeral key.
- **Browser session:** access and refresh tokens are HttpOnly, SameSite=Lax cookies; Secure is enabled in production. Unsafe cookie-authenticated requests validate origin. Frontend uses `credentials: 'include'`, not persisted bearer tokens.
- **Storage:** `db.py` uses SQLAlchemy, SQLite by default (or `DATABASE_URL`), with `jarvis_kv` storing named user/session/chat collections; domain tables/repositories are separately defined in `persistence.py`. These are not separate relational tables for each named collection.
- **Authorization:** identity is not authorization. Route-level dependencies, owner checks, role/tenant rules, API-key scope and capability-specific confirmation/policy are enforced at backend boundaries. A complete uniform policy inventory for every sensitive route remains outstanding.

Backend WebSocket endpoint is not the runtime event authority; demote duplicate state feeds as surfaces migrate. |
| Multiple task/job registries | **Split authorities** | Agent tasks, task capability persistence and control-plane jobs differ; job metadata is not proof of queued work. Keep each owner explicit until a migration is tested. |
| Provider catalog / model governance / live routing | **Different states** | Do not show configured/registered as healthy or active; event actual route and outcome. |
| Browser legacy and current browser APIs | **Compatibility + real APIs** | Legacy embedded path may report unavailable; current browser APIs have independent session ownership. |
| Scheduler, voice listening/WebSocket, video, some geography providers | **Explicitly unavailable or provider-dependent** | Preserve `NOT_CONFIGURED`/`NOT_IMPLEMENTED`; no fake successful state. |
| Dashboard components using intervals/timeouts | **Mixed** | Some are transport retry/debounce/UI timers; others poll system/task/monitoring APIs. Timer use alone does not prove fake activity. Audit each component before removal. |
| Mock providers in tests | **Test doubles, not production capability** | Test mocks are valid test fixtures. No conclusion that a production provider is available follows from them. |

## Runtime event, request identity and presentation gaps

1. **Request identity:** the legacy chat route now passes the middleware request ID to ChatService; provider calls execute within the existing `request_id_var` context and chat/runtime/audit/presentation share that ID. Other entry points have not all been proven to propagate it. Runtime presentation IDs are distinct object identities and should correlate, not impersonate request IDs.
2. **Runtime events:** canonical envelopes, sequence/snapshot reduction, redaction, authenticated session-scoped SSE and replay are implemented. The journal is process-local and capped; no shared durable runtime event store is configured.
3. **Event sources:** ChatService and capability lifecycle have explicit integration. Existing voice, image, browser, task, provider, location/device producers do not all publish or map complete lifecycle data. Payload allowlists intentionally omit private content.
4. **Presentation:** planner/contract/registry foundations exist, but web registration advertises conversation + text/status only. There is no verified full map, media, research or spatial renderer interaction path in this audit.
5. **Client runtime:** SSE updates runtime projection, while parts of activity/monitoring still use old stores, polling and sockets. Stream error/reconnect presentation and sequence-gap semantics need integration tests.

## Migration classification

| Class | Current examples | Migration rule |
|---|---|---|
| **A — Real capability environment** | Chat; configured provider; authenticated browser/geography/media APIs | Keep; move presentation choice behind semantic intent and event evidence. |
| **B — Compatibility surface** | Legacy dashboards and older browser/voice surfaces | Retain only while consumers migrate; label actual availability. |

## First implementation targets

1. **P0 — Authorization:** finish route-by-route authorization review for system operations, devices, connectors, MCP, files, admin, memory and projects. Keep all commands backend-authorized.
2. **P1 — Runtime truth:** add provider selection/start at actual gateway points; bridge real voice/browser/task/device producers; verify SSE replay through authenticated route and define multi-worker durability.
3. **P2 — Chat:** preserve one request ID through HTTP, ChatService, gateway, capability, event, presentation and audit; retain idempotency.
4. **P3/P4 — Presentation:** connect real events to planner and implement actual semantic renderer(s); advertise only renderers the client supports.
5. **P5 — Vertical slices:** web research is closest to an existing chat capability; location requires permissioned command handoff, event bridge and map renderer; image requires generated artifact attachment/rendering; voice needs configured STT/TTS and conversation session continuity.
6. **P6/P7 — Migration/expansion:** classify routes before consolidating; only then migrate device, communications, learning and multi-surface environments.

## Change control for next slices

Each code slice should record: current owner, new owner (if any), why the change is necessary, dependencies, security impact, frontend impact, backward compatibility, tests, and rollback. Prefer one capability end-to-end over broad page or file rewrites. Do not introduce a new event bus, capability registry, provider router, conversation authority, task engine, auth authority or presentation state store.
